# TX Power Calibration: Getting Flat Power Across Bands

Status: proposed procedure, not yet done. This replaces an earlier
version of this doc written against a since-superseded TX pipeline (see
§2) - its "every band clips to the same ceiling" finding no longer
applies, and none of its band-by-band numbers should be trusted anymore.
`data/hw_settings.ini`'s `[tx_band]` scale table is still real sbitx's
own bench numbers, carried over unchanged; this document explains why
those numbers are only a starting point here, and lays out a concrete
bench procedure - one popular QRP CW frequency per band, into a dummy
load - to re-derive values that hit a flat 5W at `TX_DRIVE`=50.

## 1. Background

`hw_settings.ini` carries a `[tx_band]` section per HF band, each with
an `f_start`/`f_stop` range and a `scale` value. On real sbitx, this
table comes from `calibrate_band_power()` (`sbitx.c`) - an automated
routine that keys down on a dummy load, reads real forward power back
over I2C from a power/SWR bridge board, and walks `scale` up until the
band hits its target wattage. That's genuine, bench-verified, per-band
data, compensating for the PA's own gain rolloff across HF (sbitx's own
comment: *"the PA gain varies across the band from 3.5 MHz to 30 MHz
here we adjust the drive levels to keep it up, almost level"*).

minibitx has no power/SWR bridge on this board (`sBitx DE, original` -
confirmed absent at boot), so that automatic feedback loop isn't
available here at all - any calibration has to be done by hand, watching
an external wattmeter, the same way the *board owner* originally
calibrated real sbitx itself (see the project history: "*My scale
settings are calibrated on the sbitx to produce 5 watts output with
drive = 50*"). minibitx's CW TX audio is also generated by a completely
different pipeline than sbitx's own FFT-domain modulator (see
[`../03_tx_processing_pipeline.md`](../03_tx_processing_pipeline.md)),
so reusing sbitx's `scale` *numbers* unchanged was never expected to
carry over exactly - only the relative *shape* across bands (real PA
rolloff data) is trustworthy as a starting point.

## 2. What changed since the last calibration attempt

The previous version of this doc was written when `TX_GAIN_CORRECTION`
was 4.0, and found every band's pre-clip amplitude already exceeding
`TX_SAMPLE_CLAMP` - every band saturating to the same ceiling regardless
of its `scale` entry, defeating the whole point of a per-band table.

Since then, the CW TX carrier moved from a bare 700Hz tone straight into
the balanced modulator (sitting deep inside the crystal filter's
passband on both mixing products - genuine DSB) to a carrier shifted up
by `TX_IF_OFFSET_HZ` (~23.3kHz), deliberately landing the wanted product
at the crystal filter's real measured center - its point of *least*
attenuation - instead of out on its skirt (full mechanism in
[`../03_tx_processing_pipeline.md`](../03_tx_processing_pipeline.md)'s
"Mixer 2" section). That single change meant the *old* 4.0 gain, which
had been calibrated against a signal that was losing real power to the
filter's own attenuation, now drove the same digital amplitude into a
much lower-loss path - a first re-test at the old value measured over
23W on a board whose PA had only ever been bench-confirmed safe up to
~6-8W. `TX_GAIN_CORRECTION` was re-bench-calibrated down to **0.045**
(40m/7.020MHz: 5.1W, matching real sbitx's own 4.8W on the same board at
the same drive setting) - an ~89x cut from the old value.

At 0.045, no band's pre-clip amplitude reaches `TX_SAMPLE_CLAMP` (2×10⁹)
any more - not even 10m, whose `scale` (0.0107) is the largest in the
table by roughly 14x over 80m's. That means the per-band `scale` table
can finally do the differentiating job it was always meant to do,
instead of every band collapsing to the same saturated waveform. This
doc's job now is the same as it would have been from the start if
`TX_GAIN_CORRECTION` had been right the first time: bisect each band's
`scale` by ear (well, by wattmeter) until it reads 5.0W.

## 4. Calibration procedure

No rebuild is needed between trials - `hw_settings.ini` is read once at
startup (`hw_settings_load()`, `hw_settings.c`), so each trial is just:
edit the file, restart minibitx, key down, read the meter. Into a dummy
load throughout, `TX_DRIVE` fixed at 50 (see §6 for the live-drive-control
idea this is a placeholder for).

For each of the 9 `[tx_band]` entries:

1. Tune to that band's test frequency (§3 table).
2. Key down, hold a couple of seconds, and read the **steady** wattmeter
   value (not the initial turn-on kick - see the attack-transient note
   in `sound.c`'s comments).
3. Bisect that band's `scale` value in `hw_settings.ini` up or down
   until the steady reading is ~5.0W. Record the final `scale`.
4. Move to the next band.

Since every band now has real headroom below the clamp (§2), this
should be a straightforward bisection on every band - unlike the
previous session, there's no expectation any band is ceiling-limited
going in. §7 covers what to do if one turns out to be anyway.

## 6. Future: a live 'drive' control

`TX_DRIVE` is a fixed compile-time constant (50) today - there's no live
UI or command to change it. The intent is that a future control would
let an operator dial drive above this bench-calibrated 5W-per-band
baseline, trading the "flat, safe, QRP-appropriate" default calibrated
here for more available power at their own discretion and risk (up to
whatever the PA and this bench session's headroom can actually support -
see §7 for where that runs out). Not implemented yet; recording the
intent here so the 5W target above is understood as a deliberate,
conservative default rather than a hard ceiling nobody thought to make
adjustable.

## 7. If a band can't reach 5W

If a band turns out to be genuinely ceiling-limited even after bisecting
`scale` all the way up toward the clamp, the options are, roughly in
order of effort:

- **Accept it and document the real number.** A slightly-under-5W CW
  signal on the hardest band is still a working signal; this may be
  perfectly fine for minibitx's scope as a support layer. Worth checking
  against real sbitx's own spec for this board family, which claims 40W
  on 80m/40m but only "6 watts on 10M" - if even the reference design's
  PA rolls off that hard up there, a from-scratch 5W target on 10m/12m
  may be optimistic regardless of `scale`.
- **Check for a little spare clamp headroom.** `TX_SAMPLE_CLAMP` (2×10⁹)
  is set with some margin below the true ±2.147×10⁹ a 32-bit sample
  allows. Raising the clamp closer to that limit buys a small (~7%),
  fixed amount of extra headroom - worth trying, but it's a small knob,
  not a fix for a large shortfall.
- **Look for headroom outside the digital pipeline entirely** - e.g.
  whether there's any other real analog gain stage available on this
  board. This is genuinely new investigation, not a tuning exercise,
  and shouldn't be assumed to exist without checking - PA gain rolloff
  across HF is a real hardware property, not something software can
  manufacture out of nothing.

Whatever the outcome, keep the measured-vs-target gap documented here
rather than silently accepted - a future board revision or PA change is
the kind of thing that would make it worth re-running this procedure
from scratch.
